2. 背景と目的

日常の業務導線としてLINE WORKSを活用しつつ、InstagramやXのような「投稿」「タイムライン」「いいね」「コメント」を持つ社内限定SNSを構築する。チャットツール特有の情報流出を防ぎ、ナレッジの蓄積・拡散・可視化を実現することを目的とする。機能重複を避け、軽量かつ保守性の高いシステムを目指す。

3. システムコンセプト

  • シームレスな体験：LINE WORKS内のミニアプリ（WOFF）として動作し、ログインの手間を省く。
  • 情報のストックと拡散：タイムライン形式での全社・部署ごとの情報共有。
  • 軽量・コンパクト：Go言語による単一バイナリ（モノリス）構成とSSR（Server Side Rendering）+ HTMXによる軽量フロントエンド。
  • 適度な通知：Incoming Webhookを用いた重要な投稿のみの通知連携。

4. 対象業務と利用シナリオ

  • シナリオA（日常的な発信）：営業担当者が外出先からLINE WORKSを開き、WOFFアプリ経由で商談メモや写真を社内SNSに投稿する。
  • シナリオB（情報収集）：社員が移動中にタイムラインを閲覧し、他部署の投稿に「いいね」やコメントを残す。
  • シナリオC（管理者業務）：管理者がPCブラウザからOIDC経由で管理画面にログインし、通報された不適切投稿の確認・非表示処理を行う。

5. 要件定義

5.1 業務要件

  • 社員がLINE WORKSから社内SNSへシームレスにアクセスできること。
  • 部署横断で情報発信・ナレッジ共有ができること。
  • 炎上や不適切投稿を抑止する管理・通報機能が存在すること。

5.2 機能要件

  • 投稿・閲覧：テキスト（最大4000字）、複数画像添付、ハッシュタグ機能。
  • エンゲージメント：いいね（1ユーザー1回）、コメント（1階層スレッド）、メンション機能。
  • 公開範囲制御：全社（company）、部署限定（department）、指定グループ（group）、自分のみ（private）。
  • アカウント連携：LINE WORKSユーザー情報・所属情報の自動同期（User API）。

5.3 画面要件

モバイル中心の業務向けUI（詳細は12章「画面ワイヤー」を参照）。ホームフィード、投稿作成、投稿詳細、通知一覧、プロフィール、管理画面。

5.4 権限要件

  • 一般ユーザー：自身の投稿作成・編集・削除、閲覧許可された投稿の閲覧・アクション。
  • 管理者（admin/moderator）：全投稿の閲覧、不適切投稿の削除、ユーザーの利用停止。

5.5 通知要件

アプリ内通知（メンション、コメント）およびLINE WORKSトークルームへのIncoming Webhook通知（新規重要投稿、運用通知等）。

6. アーキテクチャ設計

6.1 全体構成

フロントエンドはSSR + HTMX + Alpine.jsとし、バックエンドはGo言語によるモノリス構成。バッチ・非同期処理用にAPIサーバーとWorkerプロセスを分離してデプロイ可能な設計とする。

6.2 採用技術スタック

  • バックエンド：Go (chi/Echo)
  • フロントエンド：HTML Template (SSR), HTMX, Alpine.js, Pico CSS
  • データベース：PostgreSQL (全文検索機能利用)
  • ストレージ：S3互換オブジェクトストレージ (MinIO等)
  • インフラ/コンテナ：Docker Compose (初期運用想定)
【推奨】軽量化方針 初期フェーズではRedis等の外部キャッシュストアを導入せず、PostgreSQLでの処理に寄せる。フロントエンドも大規模SPAフレームワークを避け、WebView環境（WOFF）で初期表示が高速なSSRを採用する。

7. 認証・認可方針

7.1 WOFF起動時の考え方

LINE WORKSアプリ内からのアクセスは、WOFF SDKを通じて取得したコンテキスト情報を用いて内部用セッションCookieを発行し、以降はCookieベースで認証を行う。

7.2 OIDCログイン方針

PCブラウザや管理画面への直接アクセス時は、LINE WORKSのOIDC (Authorization Code Flow + PKCE) を用いて認証し、内部セッションを発行する。

7.3 ユーザー同期方針

初回ログイン時および定期Workerジョブにより、LINE WORKSのUser APIを呼び出し、ユーザープロフィール（表示名、アイコン）および所属部署（department）を内部データベースに同期（Upsert）する。

13. 非機能要件

  • 性能：1画面の初期ロードは2秒以内。
  • 可用性：平日業務時間帯（9:00〜19:00）の安定稼働を優先。
  • セキュリティ：全通信HTTPS。セッションCookieはHttpOnly/Secure属性付与。WOFF Endpoint URL情報のログ出力禁止。
  • 監査：投稿削除、権限変更、管理者アクションは監査ログ(audit_logs)に保存。

15. リスク・留意点

【注意】WOFF固有の制約 WOFFのEndpoint URLにはaccess_token等の重要情報が付与されるため、アクセスログ等への露出を防ぐこと。フロントエンドでの処理完了後は速やかに内部セッションへ移行する。
【注意】Incoming Webhookの制約 発行可能なURL数（最大5）やリクエスト数に制限があるため、投稿ごとの即時送信ではなく、Workerを利用したバッチ処理や重要投稿のフィルタリングを推奨する。認証用途には絶対に使用しないこと。
