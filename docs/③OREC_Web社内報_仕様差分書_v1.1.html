2. 追加コンテンツ設計

2.1 NEW 部署紹介ページ（Department Page）

概要

各部署ごとに独立したページを設け、部署の概要・メンバー・投稿フィードを一覧できる。 部署担当者（各部署の運用責任者）が入力・管理する。デモ実装の最小要件に含む。

表示コンテンツ

要素説明入力者
部署名・キャッチコピー部署の一言説明部署担当者
部署紹介文業務内容・役割の説明（任意）部署担当者
カバー画像部署イメージ画像（任意）部署担当者
メンバー一覧所属社員のサムネイル + 名前（LINEWORKSから自動同期）自動
部署フィードこの部署タグが付いた投稿の一覧（全社フィードと同一データ）自動
部署からのお知らせ2.7参照部署担当者

新規テーブル要件

既存の departments テーブルに以下カラムを追加する：

ALTER TABLE departments ADD COLUMN catchcopy TEXT;
ALTER TABLE departments ADD COLUMN description TEXT;
ALTER TABLE departments ADD COLUMN cover_image_url TEXT;
ALTER TABLE departments ADD COLUMN manager_user_id UUID REFERENCES users(id);
ALTER TABLE departments ADD COLUMN updated_at TIMESTAMPTZ DEFAULT NOW();
【デモ実装方針】 デモ段階では代表的な2〜3部署のデータを手動投入してよい。部署担当者向けの入力UIは将来実装でもよいが、表示側はデモに必要。

2.2 NEW 社員プロフィールページ（拡張フィールド）

概要

v1.0の users テーブルはLINE WORKSから自動同期される基本情報のみ。 今回、社員が自ら記入する「社内報的プロフィール」フィールドを追加する。 目的は社員間のコミュニケーション支援（趣味・人となりの共有）。デモ実装の最小要件に含む。

追加プロフィールフィールド

フィールド必須/任意最大文字数備考
趣味・関心任意200字複数入力可（タグ形式推奨）
得意なこと・スキル任意200字
一言メッセージ任意100字プロフィール画面の上部に表示
入社年任意年数（数値）
キャリア経歴任意500字任意。キャリアインタビュー（2.5）とも連携
プロフィール写真任意-LINE WORKSのアイコンとは別に社内報用を設定可
【必須フィールドの方針】 キャリア経歴以外は必須とすると入力負荷が高いため、全て任意とする。 ただし、入力完了率をKPIとして効果測定に含め、未入力の場合は「プロフィールを完成させよう」の促しUIを表示する（入力完了率が効果測定指標の一つ）。
【初期入力の進め方】 オフィス勤務のメンバーに先行して入力してもらい、製造スタッフは後追い。 管理者がプロフィール入力完了率を確認できるダッシュボード機能をPhase 2以降に実装する。

新規テーブル

CREATE TABLE user_profiles (

    joined_year     SMALLINT,

2.3 変更 全社フィード（複数部署タグ対応）

変更内容

v1.0では投稿の visibility_department_id が単一FK（1部署のみ）。 今回、「営業部が製造部の頑張りを投稿する」などのクロス部署投稿ニーズに対応するため、 投稿に複数部署タグを紐付けられる多対多構成に変更する。

【v1.0からの変更】 posts.visibility_department_id（単一FK）を廃止し、post_department_tags中間テーブルで管理する。 公開範囲（company / department / private）の制御は posts.visibility_type で引き続き行う。

テーブル変更

-- posts テーブルから以下カラムを削除（v1.0との差分）
-- visibility_department_id UUID FK → 廃止

-- 新規中間テーブルを追加
CREATE TABLE post_department_tags (
    post_id       UUID REFERENCES posts(id) ON DELETE CASCADE,
    department_id UUID REFERENCES departments(id) ON DELETE CASCADE,
    PRIMARY KEY (post_id, department_id)
);

-- 部署フィード取得例
SELECT p.* FROM posts p
JOIN post_department_tags pdt ON pdt.post_id = p.id
WHERE pdt.department_id = $1
ORDER BY p.created_at DESC;

UI仕様

  • 投稿作成フォームで「部署タグ」を複数選択できるチェックボックスUIを追加。
  • タグ付けした部署は投稿カードに表示（例: #製造部 #品質管理部）。
  • タグ付きの投稿は全社フィードに流れ、かつ該当部署ページの部署フィードにも表示される。
  • 公開範囲「部署限定」の場合、選択した部署のメンバーのみに表示。

2.4 NEW サンクスカード（ピアボーナス機能）

概要

社員が他の社員へ感謝・称賛を送る機能。通常の「いいね」とは別の独立した機能として設計する。 送付枚数はインセンティブ表彰の評価基準に組み込まれる（OREC HD人事部門と要連携）。

仕様

項目仕様
送付単位ユーザー → ユーザー（投稿とは独立して送付可能）
メッセージ必須・最大200字
月次上限1ユーザーあたり送付枚数に上限を設ける（具体的な枚数は 要確認）
公開範囲全社公開（全社フィードに流れる）
いいね連携サンクスカードの投稿にもいいね・コメント可能
インセンティブ連携受取枚数を月次・年次で集計し、人事評価の参考指標とする
ランキング月次の受取枚数ランキングをサイネージモードに表示（3章参照）

新規テーブル

CREATE TABLE thanks_cards (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    sender_id     UUID NOT NULL REFERENCES users(id),
    receiver_id   UUID NOT NULL REFERENCES users(id),
    message       TEXT NOT NULL,
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    -- 月次上限チェック用
    CONSTRAINT no_self_send CHECK (sender_id != receiver_id)
);

CREATE INDEX idx_thanks_cards_receiver ON thanks_cards(receiver_id, created_at);
CREATE INDEX idx_thanks_cards_sender   ON thanks_cards(sender_id, created_at);

-- 月次上限チェック用ビューまたは関数
-- 例: 1ユーザーの当月送付枚数を取得
-- SELECT COUNT(*) FROM thanks_cards
-- WHERE sender_id = $1
--   AND created_at >= date_trunc('month', NOW());

2.5 NEW キャリアインタビュー記事（AI生成）

概要

社員が社員をインタビューし、その内容をAIが記事化する。四半期に1本程度の発行を想定。 記事データはDB管理し、社内報の「特集記事」として専用ページで表示する。

制作フロー

ステップ作業内容担当
①テーマ・被インタビュアー選定人事/広報担当者が決定OREC HD
②インタビュー実施社員が社員にインタビュー（録音・メモ）OREC HD
③AI記事生成インタビュー素材をAIに入力し記事原稿生成AIアシスト（要外部連携 or 管理画面機能）
④確認・編集人事/広報担当者が確認・修正して公開OREC HD
【AI生成の実装方針】 Phase 3では管理画面にインタビュー原稿テキストを入力すると記事HTMLを生成するフォームを設ける（外部LLM API呼び出し）。 Phase 3未満の段階では、管理者がHTMLを直接入力して記事を登録する方法でよい。

新規テーブル

CREATE TABLE career_articles (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    subject_user_id UUID REFERENCES users(id),     -- 記事の主人公
    interviewer_user_id UUID REFERENCES users(id), -- インタビュアー
    title           TEXT NOT NULL,
    body_html       TEXT NOT NULL,                 -- 記事本文（HTML）
    thumbnail_url   TEXT,
    published_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    status          TEXT DEFAULT 'draft'           -- draft / published
);

2.7 NEW 部署からのお知らせ

概要

各部署が発信する「お知らせ」投稿。通常の全社フィード投稿と同じデータ構造を使い、 post_type = 'announcement' フラグで区別する。 全社フィードにも流れ、かつ当該部署ページにも表示される。

テーブル変更（postsへの追加）

-- posts テーブルにカラム追加
ALTER TABLE posts ADD COLUMN post_type TEXT DEFAULT 'post';
-- post_type: 'post'（通常投稿）/ 'announcement'（お知らせ）/ 'thanks_card'は別テーブルで管理

-- お知らせ一覧取得例
SELECT * FROM posts
WHERE post_type = 'announcement'
  AND $department_id = ANY(SELECT department_id FROM post_department_tags WHERE post_id = posts.id)
ORDER BY created_at DESC;

UI仕様

  • 投稿作成フォームに「投稿種別：通常投稿 / 部署からのお知らせ」の選択UIを追加。
  • お知らせ投稿はフィード内で視覚的に区別（バッジ表示やカード背景色変更など）。
  • 部署ページのお知らせタブで一覧表示。

3. NEW サイネージモード（製造スタッフ向け）

概要

製造スタッフはスマートフォンを業務中に使用できず、休憩時間も短い。 これを解決するため、休憩スペースのモニター向けに専用のサイネージ表示モードを設計する。

アクセス方法

項目仕様
URL通常版と別URL（例: sharonai.orec.jp/signage）で独立した画面として提供
認証ログイン不要。社内ネットワークのIPアドレス制限のみで制御
運用方法ブラウザでサイネージURLを開きっぱなしにするだけ（特別なハードウェア不要）
モニター管理要確認 各拠点に委ねる想定だが、設置場所・台数を確認する

表示コンテンツ

コンテンツ更新頻度データソース
全社フィードの最新投稿リアルタイム（ポーリング）/api/feed?type=signage
今日の記念日・イベント（四半期カレンダー連動）毎日カレンダーマスタ
社員プロフィールのピックアップ（ランダムローテーション）定期（数分ごと）/api/users/random-profile
部署紹介のローテーション定期（数分ごと）/api/departments/signage
サンクスカード獲得ランキング（月次）月次更新/api/thanks-cards/ranking

実装仕様

  • サイネージ用エンドポイントはIPアドレス制限ミドルウェアで保護する。
  • フロントエンドはSSR + JavaScriptの定期ポーリング（30〜60秒間隔）で自動更新。
  • ページ全体をコンテンツがローテーションするカルーセル形式で実装する。
  • フォントサイズ・コントラストはモニター表示（遠距離閲覧）に最適化する。

新規エンドポイント

GET /signage                    # サイネージ表示ページ（HTML、認証不要＋IP制限）
GET /api/signage/feed           # サイネージ用フィードデータ（JSON）
GET /api/signage/profile/random # ランダム社員プロフィール
GET /api/signage/department     # 部署紹介ローテーションデータ
GET /api/signage/calendar       # 今日の記念日・イベント

カレンダーマスタテーブル

CREATE TABLE event_calendar (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_date DATE NOT NULL,
    title      TEXT NOT NULL,
    description TEXT,
    source     TEXT DEFAULT 'internal'   -- 'internal' / 'x_calendar'
);
【X（Twitter）イベントカレンダー連携について】 四半期ごとにXが公開するイベントカレンダーを参照し、管理者がカレンダーマスタに手動登録する運用でよい。自動取得APIは将来対応。

4. NEW 投稿ガイドライン・リテラシー対策

ガイドラインの設置

設置場所仕様
投稿フォーム内フォーム下部に常時表示（折りたたみ可）
初回ログイン時ガイドライン全文の確認・同意フローを実装。同意なしには投稿不可

ガイドラインの内容・管理

項目仕様
ガイドライン作成サンカクキカクが叩き台を作成 → ORECが確認・追加して確定
主な内容写真の写り込み防止 / 個人情報の取り扱い / 言葉遣いの注意事項
更新・管理月額運用費の範囲内でサンカクキカクが継続対応
更新時の対応ガイドライン更新時は既存ユーザーに再同意を促す通知を送る（要確認）

問題投稿への対応フロー

  • 投稿前の自動フィルタリングは実装しない（即時性を優先）。
  • ガイドラインの周知徹底と通報機能（v1.0 Phase 3実装済み）の組み合わせで対処。
  • 問題発生後は管理者が通報一覧から非表示・削除処理を行う（v1.0仕様通り）。

新規テーブル

CREATE TABLE posting_guidelines (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    version     TEXT NOT NULL,               -- バージョン番号（例: "1.0"）
    body_html   TEXT NOT NULL,               -- ガイドライン本文（HTML）
    published_at TIMESTAMPTZ DEFAULT NOW(),
    is_current  BOOLEAN DEFAULT TRUE         -- 最新版フラグ
);

-- ユーザーの同意記録
CREATE TABLE guideline_consents (
    user_id         UUID REFERENCES users(id),
    guideline_id    UUID REFERENCES posting_guidelines(id),
    consented_at    TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (user_id, guideline_id)
);

API追加

GET  /api/guidelines/current          # 現在のガイドライン取得
POST /api/guidelines/consent          # 同意記録
GET  /api/guidelines/consent/check    # 同意済みチェック（投稿前バリデーション用）
