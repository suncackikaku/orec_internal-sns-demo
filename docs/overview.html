社内SNSデモ 現況仕様書

LINE WORKS（WOFF）連携を前提とした社内限定SNSのデモアプリケーション。React + Go + PostgreSQL を Docker Compose で 3 コンテナ構成、ConoHa VPS 上で稼働中。本書はリポジトリ実装から起こした現時点の仕様と、README との乖離・未実装領域をまとめたもの。

01サマリー

社員が互いの人となりを知るための社内向けSNS。部署紹介・社員プロフィール・フォロー・いいね・フィード・全文検索・リアルタイムお知らせ（SSE）までが動作する。認証は LINE WORKS のミニアプリ基盤 WOFF に依存し、ブラウザ単体では利用できない構成。

いま押さえておくべき 3 点

  • 投稿を作る手段が存在しない。 posts テーブルへの書き込み API も UI も未実装で、表示される投稿は db/init.sql のシード 7 件のみ。フィード・いいね・投稿検索はすべてこの固定データの上で動いている。
  • README と実装がずれている。 README は「メール／パスワードでログイン」と書くが、現在のログイン画面は LINE WORKS ボタンのみ。/api/auth/login と /api/auth/register は UI から到達できないデッドコードとして残存している。
  • WOFF 認証にサーバー側検証がない。 フロントから送られた userId をそのまま信頼してログイン／ユーザー作成しており、任意のユーザーになりすませる。詳細は 10. セキュリティ所見。

02システム構成

Docker Compose の 3 サービス。ブラウザからは 80 番の Nginx のみが窓口で、/api は Nginx がコンテナ内の Go API へリバースプロキシする。API の 8080 もホストに公開されているため、Nginx を経由しない直接アクセス経路も開いている。

お知らせ（activities）が発火する契機

  • user_registered — ローカル登録時、および WOFF 初回ログインでユーザーが自動作成されたとき
  • profile_update — プロフィール更新時
  • 生成された activity は DB に保存され、同時に接続中の全 SSE クライアントへブロードキャストされる（activityClients マップ + mutex）

06データモデル

主キーはすべて UUID。users.updated_at はトリガー update_updated_at_column() で自動更新。followers と likes は複合 UNIQUE 制約で二重登録を防いでいる。

インデックス

  • idx_followers_following / idx_followers_follower — フィードのフォロー解決用
  • idx_likes_post / idx_likes_user — いいね集計用
  • idx_users_woff_id — WOFF ログイン時のユーザー引き当て用

シードデータ

部署 6 件、ユーザー 7 名（全員 password123 の bcrypt ハッシュ、auth_provider = 'local'）、プロフィール 7 件、投稿 7 件。カバー画像・プロフィール画像はすべて Unsplash の外部 URL を直接参照している。

07認証フロー

起動時に AuthContext が WOFF SDK を初期化し、localStorage のトークンがあれば /api/auth/me で復元する。SDK が読み込めない環境（通常のブラウザ）では初期化に失敗し、ログインボタンが押せないまま止まる。

1.  index.html    WOFF SDK (static.worksmobile.net/.../3.6/sdk.js) を読み込み
2.  AuthContext   woff.init({ woffId: 'kJAM8fCbiHyzK75Hi9y5bQ' })
3.  LoginPage     「LINE WORKSでログイン」→ woff.getProfile()
4.  POST /api/auth/woff   { userId, displayName, domainId }
5.  API           woff_id で users を検索
                    ├ 見つかる  → そのユーザーで続行
                    └ 見つからない → users + user_profiles を新規作成
                                      activities に user_registered を記録 → SSE 配信
6.  API           HS256 / 24h の JWT を発行して返却
7.  Frontend      localStorage['token'] に保存、以降 Authorization: Bearer で送信
  • WOFF ID kJAM8fCbiHyzK75Hi9y5bQ は AuthContext.jsx にハードコードされている（秘匿値ではないが環境変数化が望ましい）。
  • WOFF 経由で作成されたユーザーの email は {userId}@lineworks という合成値、primary_department_id は NULL。部署を割り当てる手段は現状ない。
  • auth/woff.go に GetAccessToken() / VerifyWoffUser() が実装済みだが、どこからも呼ばれていない。
  • authMiddleware は JWT のクレームからユーザー情報を組み立てるだけで DB 照合しない。ユーザー削除後もトークン有効期限内は通る。

10セキュリティ所見

守れている点

  • SQL はすべてプレースホルダ（$1）でパラメータ化。ILIKE 検索や動的 WHERE 組み立ても引数は分離されており、文字列連結は列名・演算子のみ。
  • 保護ルートは chi の Group + authMiddleware でサーバー側強制。クライアントの PrivateRoute だけに依存していない。
  • パスワードは bcrypt（DefaultCost）でハッシュ化。JWT は HS256 / 24 時間で失効。
  • .env は .gitignore 済み。フロントの VITE_ 変数は API パス（/api）のみで、秘匿値のバンドル混入なし。

要対応

CRITICAL WOFF 認証でなりすましができる api/main.go:1055

フロントから送られた userId / displayName / domainId を一切検証せずに DB 照合し、未登録なら新規作成して JWT を発行している。curl で任意の userId を POST すれば、他社員として、あるいは架空の社員としてログインできる。auth/woff.go の VerifyWoffUser() は実装されているが呼ばれていない。

対応フロントから woff.getAccessToken() のトークンを送り、サーバーで LINE WORKS API に問い合わせて userId を確定してから認証する。検証が通らないリクエストは 401 で落とす。
HIGH JWT_SECRET のフォールバックがハードコード api/main.go:227

環境変数が未設定でも "your-secret-key-change-in-production" で起動してしまう。.env の設定漏れに気付けず、既定鍵のまま本番稼働するとトークンを自由に偽造される。

対応未設定なら log.Fatal で起動を止める。あわせて 32 文字以上を要求する。
HIGH ビルド済みバイナリがリポジトリにコミットされている api/api · api/main.exe（各 11MB）

.gitignore に api/api があるが、追加済みファイルには効かず追跡され続けている。main.exe は無視設定にも入っていない。合計 22MB がリポジトリを膨らませているうえ、ビルド時の環境情報や埋め込み文字列が公開される。

対応git rm --cached api/api api/main.exe のうえ .gitignore に api/main.exe を追加する。
MEDIUM CORS が全オリジン許可 api/main.go:237

AllowedOrigins: ["*"] かつ AllowedHeaders: ["*"]。8080 がホストに直接公開されているため、任意のサイトのスクリプトから API を叩ける。認証はトークン方式なので即時の情報漏洩にはならないが、防御層としては空いている。

対応本番ドメイン（https://orec-demo-app.suncac.net）に限定し、8080 の公開自体も Nginx 経由に絞ることを検討する。
MEDIUM DB 認証情報が docker-compose.yml に直書き docker-compose.yml:8-10

snsuser / snspassword がリポジトリに平文で入っている。5433 がホストに公開されているため、VPS のファイアウォール設定次第では外部から直接接続を試みられる。

対応.env 参照（${POSTGRES_PASSWORD}）に変更し、パスワードをローテーションする。5433 の公開ポートは開発時のみに限定する。
LOW SSE のトークンをクエリ文字列で送信 api/main.go:293 / WelcomePage.jsx:38

EventSource がヘッダを付けられないための回避策だが、JWT が Nginx のアクセスログ・Referer・ブラウザ履歴に残る。

対応SSE 用に短命の使い捨てトークンを発行するか、Nginx 側で当該パスのクエリをログから落とす。

任意改善（やっておくと堅い）

  • ログイン API にレート制限。 go-chi/httprate を /api/auth/* に噛ませる（例：1 分 10 回）。総当たりと大量ユーザー自動生成の両方を抑えられる。
  • プロフィール画像 URL の検証。 ユーザーが任意 URL を保存できるため、https スキームと許可ホストに限定して外部トラッキングや不正スキームを防ぐ。
  • authMiddleware で DB 照合を 1 回入れる。 退職・削除したユーザーのトークンを即時無効化できる。
  • 専用ヘルスチェック /api/health の追加。 現状 deploy.sh がデータ取得 API で生死判定しており、DB 障害と API 障害を切り分けられない。
  • エラー応答の整形。 http.Error(w, err.Error(), 500) が多用され、SQL のエラー文がそのままクライアントに返る。内部情報を隠したメッセージに統一する。
